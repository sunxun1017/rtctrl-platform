# JPEG 分帧优化实测

| 轮次 | 修改前，ms/帧 | 修改后，ms/帧 |
| --- | ---: | ---: |
| 1 | 2.045 | 0.475 |
| 2 | 2.054 | 0.472 |
| 3 | 2.034 | 0.454 |

平均从 2.044 ms/帧降到 0.467 ms/帧，这个固定样本上的分帧测试 CPU 时间减少约 77.2%。

| 测试顺序 | 总 CPU | Python CPU | GStreamer CPU | FPS |
| --- | ---: | ---: | ---: | ---: |
| before-1 | 34.74% | 7.91% | 26.83% | 30.011 |
| after-1 | 27.92% | 3.33% | 24.59% | 30.062 |
| after-2 | 29.37% | 3.24% | 26.13% | 30.065 |
| before-2 | 33.84% | 7.86% | 25.98% | 30.059 |

这里 CPU 都按一个核为 100%。Python 均值从 7.89% 降到 3.29%，减少约 58.4%；两进程合计从 34.29% 降到 28.64%。GStreamer 侧也有波动，所以不能把总量的全部下降都算成分帧器的收益。

| perf 观察 | 修改前 | 修改后 |
| --- | ---: | ---: |
| cpu-clock 样本数 | 663 | 536 |
| 丢失样本数 | 0 | 0 |
| `_PyEval_EvalFrameDefault` Self | 7.54% | 1.49% |
| 同轮 Python CPU，占单核 | 7.96% | 3.38% |

还有一个容易误读的例子：cache clean 的 Self 从 11.76% 变成 12.13%，看起来反而高了，但这两轮总样本数也不同，换算后分别约 78 和 65 个样本。因此不能仅凭占比上升就认定缓存维护变慢了，更不能把这些短测样本当作精确耗时。

不带 perf 的四轮与带 perf 的两轮分开记录；实时画面短测，不代表所有场景。已部署 Python 修改，系统 MPP 插件保持原版。
