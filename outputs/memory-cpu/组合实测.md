# 单内存、池复用与 JPEG 输出组合实测

这是 2026-09-12 的独立预览历史实验，不运行人脸模型。三组都使用单内存 NV12；A 关闭转换缓冲复用、保留 zero-copy-pkt=true，B 开启复用且保持 true，C 开启复用并改为 false。每组预热超过 60 帧后测约 20 秒，按 A/B/C/C/B/A 顺序执行，板内一个 MJPEG 消费者持续取流。

| 顺序 | 组合 | CPU | FPS | PSS 范围，MiB | 可见 DMA-BUF，MiB | 对象数 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 1 | A | 10.84% | 30.002 | 21.98–22.05 | 11.46–11.46 | 4–4 |
| 2 | B | 9.26% | 30.044 | 21.83–21.99 | 12.45–12.45 | 5–5 |
| 3 | C | 7.78% | 30.047 | 22.04–22.16 | 11.46–11.46 | 4–4 |
| 4 | C | 7.79% | 30.059 | 22.03–22.09 | 11.46–11.46 | 4–4 |
| 5 | B | 9.21% | 30.044 | 21.31–22.00 | 12.45–12.45 | 5–5 |
| 6 | A | 10.79% | 30.053 | 19.57–22.11 | 11.46–11.46 | 4–4 |

A、B、C 的 CPU 均值分别为 10.81%、9.23%、7.78%。在单内存输入已经成立的条件下，缓冲复用继续省下一部分 CPU；关闭 JPEG 包零拷贝又省下一部分。C 比 B 的 CPU 均值低约 15.7%。这次多一份压缩包复制反而更省 CPU，不能据此推广成所有复制都值得增加。

B 的可见 DMA 对象比 A 多一个，大小相差 1,040,384 字节，和之前的缩放缓冲大小吻合；C 的快照回到四个对象。它反映的是对象持有方式发生了变化，不是证明系统全部 DMA 分配少了同样大小。PSS 没有出现 MiB 级膨胀，但也没有明显下降，不能把这个改动宣传成大幅节省进程内存。

NPU 120 次观测全部 0%；当前独立预览不加载 RKNN。实验组合未默认部署。

## 再用 perf 核对 JPEG 输出

另外各跑一轮约 18 秒的 `perf record -e cpu-clock -F 99 -g`，两轮都开启转换缓冲复用，只改 zero-copy-pkt。开启详细采样的这两轮不并入前面六轮 CPU 均值。

| 观察 | zero-copy-pkt=true | zero-copy-pkt=false |
| --- | ---: | ---: |
| cpu-clock 样本数 | 153 | 125 |
| 丢失样本数 | 0 | 0 |
| 编码输出线程的 `__arch_copy_from_user` Self | 21.57% | 1.60% |
| 同线程的 `__pi_dcache_clean_poc` Self | 5.23% | 13.60% |

管道复制热点降了，但缓存维护和用户态 libc 仍有成本。这更符合“工作转移到了另一条复制和内存访问路径”，而不是整段复制消失。153 和 125 个样本很少，不拿这些占比推精确延迟，也不据此认定缓存属性是唯一原因；总 CPU 的判断仍以前面不带详细追踪的对照为主。
