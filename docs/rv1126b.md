# ALIENTEK ATK-DLRV1126B deployment

## Scope

The ATK-DLRV1126B is an ARM64 Linux 6.1 deployment target built around the
RV1126B/BJ. The portable model, control, safety,
runtime, protocol, IPC, POSIX platform, serial, and SocketCAN layers are reused
without SoC conditionals. Board-specific BSP, device tree, camera sensor, RKISP,
RKNN, and actuator wiring remain leaf integrations.

The board provides two MIPI CSI, two CAN FD, two RS485, Gigabit Ethernet, USB,
and an external RTC. The initial support boundary is deliberately userspace-only.
It does not claim that the ATK-DLRV1126B has the mailbox endpoint described by the
rtctrl kernel UAPI, PREEMPT_RT enabled, or a configured camera sensor.

## Cross-build

The vendor SDK is a `repo` multi-repository archive, not a single Git repository.
Its reproducible identity is locked in `platforms/atk-dlrv1126b/sdk.env`: release
`atk-dlrv1126b-linux6.1-v1.2.0-20260425`, manifest commit `a614e6d`. Check a local
archive without changing it:

```bash
./scripts/check-linux-sdk.sh \
    --platform atk-dlrv1126b \
    --sdk-root /home/sx/projects/atk_dlrv1126b_linux6.1_sdk
```

The downloaded package initially stores source Git objects below `.repo`; run
its `./repo.sh` once to materialize the worktrees. Buildroot must then generate
the target toolchain before rtctrl can consume the SDK directly:

```bash
./scripts/cross-build-linux-userspace.sh \
    --platform atk-dlrv1126b \
    --sdk-root /absolute/path/to/atk_dlrv1126b_linux6.1_sdk \
    --plan
```

## Public kernel and board overlay

The reproducible kernel path does not depend on the vendor's LAN Git server.
`third_party/linux-rv1126b` pins Rockchip's public `develop-6.1` kernel, while
`platforms/atk-dlrv1126b/bsp/kernel` carries only the Alientek board config and
default 720x1280 device tree. Prepare or validate it with:

```bash
git submodule update --init --depth 1 third_party/linux-rv1126b
./scripts/prepare-linux-kernel-source.sh \
    --platform atk-dlrv1126b \
    --plan
./scripts/prepare-linux-kernel-source.sh \
    --platform atk-dlrv1126b \
    --build-dtb \
    --jobs 8
```

The prepared source and build output are content-addressed below `.deps/`, so a
kernel or overlay update cannot silently reuse the previous result. U-Boot,
rkbin, Buildroot, RKAIQ tuning files, and complete firmware packaging remain
locked to the vendor SDK; replacing each of those requires an independently
verified public upstream revision.

Use the toolchain installed from the ATK-DLRV1126B SDK. Its standard Buildroot
layout allows the script to derive the sysroot automatically:

```bash
./scripts/cross-build-linux-userspace.sh \
    --platform atk-dlrv1126b \
    --toolchain-bin /opt/atk-dlrv1126b-toolchain/bin \
    --plan

./scripts/cross-build-linux-userspace.sh \
    --platform atk-dlrv1126b \
    --toolchain-bin /opt/atk-dlrv1126b-toolchain/bin
```

The board profile defaults to `aarch64-buildroot-linux-gnu`. A manually unpacked
SDK can provide both paths explicitly:

```bash
./scripts/cross-build-linux-userspace.sh \
    --platform atk-dlrv1126b \
    --toolchain-bin /absolute/path/to/toolchain/bin \
    --sysroot /absolute/path/to/rv1126b/sysroot \
    --target-triple aarch64-buildroot-linux-gnu
```

The build is placed in `build/atk-dlrv1126b` and the installable runtime package
is staged under `.deps/stage/atk-dlrv1126b` by default. Both paths are ignored by Git.

The equivalent low-level CMake entry is:

```bash
cmake --preset atk-dlrv1126b \
    -DRTCTRL_TOOLCHAIN_BIN=/opt/atk-dlrv1126b-toolchain/bin \
    -DRTCTRL_SYSROOT=/absolute/path/to/rv1126b/sysroot \
    -DRTCTRL_TARGET_TRIPLE=aarch64-buildroot-linux-gnu
cmake --build --preset atk-dlrv1126b -j8
```

## Runtime architecture

Camera capture and inference must not execute in the 1 kHz I/O thread or the
200 Hz control thread. The intended single-SoC deployment is:

```text
MIPI sensor -> V4L2/RKISP -> RKNN worker -> fixed-size semantic target
                                              |
                                              v
source thread -> target SPSC -> control thread -> command SPSC -> I/O thread
                                                               -> actuator HAL
```

Frames stay in a camera-owned buffer pool. Only a bounded, timestamped semantic
result crosses into `ICommandSource`. The result must carry capture time,
sequence, confidence, and a validity deadline so stale vision cannot refresh a
control command.

## Target validation

First validate the existing runtime without a camera or physical actuator:

```bash
./rtctrl_demo --duration 10 --arm --no-mlock
./rtctrl_bench 60 1000
```

Then repeat with the production kernel and acceptance gates:

```bash
RTCTRL_MAX_JITTER_US=200 \
RTCTRL_MAX_SKIPPED_PERIODS=0 \
RTCTRL_REQUIRE_FIFO=1 \
RTCTRL_REQUIRE_MLOCK=1 \
./rtctrl_bench 60 1000 3 80
```

The CPU number and thresholds are deployment values, not platform defaults.
Repeat the benchmark while camera capture, ISP, encoding, and NPU inference are
all active. A passing idle measurement is not a production real-time result.

Before enabling a physical actuator, verify the BSP provides:

- a 64-bit userspace with lock-free 64-bit atomics;
- `CLOCK_MONOTONIC` absolute sleeps and the required pthread APIs;
- the selected UART or SocketCAN driver with bounded I/O behavior;
- sufficient `RLIMIT_MEMLOCK` and `SCHED_FIFO` privileges;
- CPU-frequency, IRQ-affinity, thermal, and PREEMPT_RT settings measured on the
  exact carrier and image.

## Verified board profile

The local vendor archive was verified against its clean `repo` checkout. Its
default board selection is
`01_atk_dlrv1126b_automipi_defconfig`, which selects:

- kernel config `alientek_rv1126b_defconfig`;
- device tree `rv1126b-alientek-mipi720x1280` with 800x1280 and 1080x1920
  alternatives;
- Buildroot config `alientek_rv1126b`.

The kernel contains and enables the OV13850 driver, including its 4224x3136
mode. The shipped Alientek board DTS currently declares IMX415, IMX335, and
IMX586 sensor nodes, not OV13850. ATK-MCOV13850 support therefore still requires
an explicit board DTS sensor node with verified I2C address, MIPI lane mapping,
clock, reset/power GPIOs, regulators, and matching RKISP tuning data. Do not
reuse another board's DTB merely because it uses the same SoC.
