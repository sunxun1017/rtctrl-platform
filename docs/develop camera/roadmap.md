# RV1126B 边缘智能视觉产品技术规划

## 1. 产品定位

不要做“摄像头 + 一个目标检测模型 + 一个网页”的 Demo。建议把当前 ATK-DLRV1126B/RV1126B 做成：

> 面向工业和机器人现场的边缘智能感知节点：端侧完成低延迟采集、轻量推理、跟踪和事件判断；复杂语义理解、数据闭环和模型管理由更强的边缘服务器或云端完成。

第一款产品只选择一个可验收的场景，例如：

- 人员进入机器人/叉车危险区域；
- 设备指示灯或仪表状态巡检；
- 物料是否到位、缺件或错件；
- 机器人工作区的异常停留或入侵。

不要一开始做“什么都能识别”。产品的含金量来自：真实环境可用、断网可用、结果可解释、故障可恢复、版本可追溯，而不是模型名字多。

## 2. 适合当前硬件的前沿主线

### 2.1 端云协同

RV1126B 适合低功耗、低延迟、隐私优先的端侧任务；大模型、跨设备分析和复杂问答放到更强节点：

```text
RV1126B：MIPI/ISP/轻量模型/跟踪/事件状态机/本地闭环
边缘服务器：多路融合/较大模型/复杂规则/设备群分析
云端：数据标注/训练/模型注册/OTA/运营报表
```

端侧不应每帧上传视频，而应输出带证据的语义事件，至少包含：`schema_version`、`device_id`、`boot_id`、`sequence`、`capture_time`、`publish_time`、`valid_until`、`model_version`、`confidence`、`health` 和证据文件 hash。这样可以做到断网本地判断、网络恢复后幂等重传，并支持问题复盘。

### 2.2 从单帧检测到时空事件理解

技术链路应是：

```text
检测 -> 多目标跟踪 -> 区域/线段/姿态关系 -> 时间窗口 -> 事件状态机 -> 告警策略
```

事件引擎应支持目标 ID、轨迹、ROI、越界线、停留时间、运动方向、遮挡恢复、连续帧确认、告警冷却和证据帧。建议状态为：

```text
UNKNOWN -> NORMAL -> SUSPECT -> ACTIVE -> RECOVERING -> NORMAL
                  \-> FAULT
```

相机断流、模型超时、温度过高、磁盘不足时必须进入 `FAULT`，不能把“没有检测到目标”当成“现场安全”。

### 2.3 面向 NPU 的模型工程

当前仓库的 RV1126B 内核已启用 `RKNPU`，但“模型能转换”不等于“产品可部署”。建立完整链路：

```text
数据集版本 -> 训练 -> 量化校准 -> RKNN 转换 -> 板端 benchmark
    -> 精度回归 -> 延迟/温度/内存验收 -> 签名发布 -> 回滚
```

每个模型都要有 model card，记录任务、类别定义、数据来源、输入尺寸、颜色空间、归一化、量化方式、转换工具版本、目标 SoC、precision/recall/F1 或 mAP、板端推理耗时、端到端延迟、内存、温度、已知失败样本和适用边界。

模型路线建议是：轻量检测/分类闭环 -> 跟踪与规则 -> 剪枝/蒸馏/INT8 量化 -> 事件触发式高质量推理。不要把端侧大视觉语言模型作为 RV1126B 的主卖点；更合理的是端侧结构化感知，边缘服务器做视觉语言解释和检索。

### 2.4 多模态感知

多模态不应只是接一个大模型。可以融合：RGB 视觉、目标轨迹、光流/帧差、光照/温度/麦克风/IMU，以及机器人状态、急停、执行器故障和工作模式。

端侧只做确定性、低延迟、可验收的判断；复杂语义描述、报告生成和跨设备关联由上层完成。这条路线既有前沿性，也符合 RV1126B 的算力和可靠性边界。

## 3. 必须保持的系统边界

当前仓库已有 1 kHz I/O、200 Hz 控制、固定容量 IPC 和安全租约。视觉系统不能进入这两个实时线程，也不能让 AI 线程直接写电机：

```text
相机/AI 非实时域
  -> 有界、带时间戳、置信度、有效期的视觉语义消息
  -> 安全策略/权限/限幅/状态机
  -> 控制域
  -> 仅允许经过验证的状态或目标
```

“检测到人”最多触发“请求减速/进入安全状态”，不能绕过急停、限位、租约和硬件安全机制。视觉结果必须允许 `unknown`，不能强迫系统在不可信时给出“正常”。

建议新增目录边界：

```text
apps/vision-camera/
  camera-service/       # V4L2、RKISP、buffer pool、断流恢复
  preprocess/           # RGA/CPU 格式和尺寸转换
  ai-service/           # RKNN 模型、NPU worker、指标
  tracking/             # 跟踪和轨迹
  event-engine/         # 规则和时空状态机
  device-agent/         # 配置、健康、升级、远程诊断
include/rtctrl/vision/  # 稳定消息，不放 RKNN 细节
tests/vision/            # 回放、状态机、故障和协议测试
tools/vision/            # 采集、转换、benchmark、诊断包
models/                  # manifest/model-card，不提交大二进制
```

## 4. 技术主线和必须完成的产物

### 4.1 相机、设备树和 ISP

围绕当前 `OV13850 + CSI1` 路径完成：

- 核对真实模组的 chip ID、I2C 地址、xvclk、供电、reset/pwdn GPIO、MIPI lane；
- 核对设备树 mode、分辨率、帧率、曝光范围和实际像素格式；
- 写 V4L2 能力探测和采集工具；
- 统计 FPS、丢帧、断流、时间戳倒退、CRC/ECC/FIFO 错误；
- 记录 RKISP/RKAIQ 调参版本和真实镜头型号；
- 覆盖低照度、逆光、闪烁、运动模糊和遮挡；
- 完成长稳采集和断流恢复测试。

不要只验收“能显示画面”，而要验收“格式、时间、错误和恢复都可证明”。

### 4.2 数据闭环和模型发布

建立：

```text
现场采集 -> 元数据 -> 清洗 -> 标注 -> 版本化切分
       -> 训练/量化 -> 板端回放 -> 错误样本回流
```

训练、验证、测试集必须按场景/设备/时间隔离，不能把相邻视频帧随机打散制造虚高分数。保存困难样本：逆光、夜间、遮挡、远近目标、空场景、相似背景和目标缺失。

业务指标应包含每小时误报数、漏报数、事件确认延迟和用户告警疲劳，而不只是 mAP。

### 4.3 端侧运行时

相机、预处理、推理、后处理、事件和上传都要有界。网络、磁盘和日志不能阻塞采集线程；优先复用 DMA buffer，减少无意义的 RGB/NV12 拷贝；统计 capture-to-decision 的 P50/P95/P99，而不是只看 NPU 时间。

运行时必须支持模型 warm-up、超时、错误码、重新加载、版本检查、降帧和降级。服务要有明确启动顺序、有限重试、退避、优雅退出、systemd/supervisor 拉起和健康接口。

### 4.4 事件协议和可观测性

事件需要幂等：断网重传、服务重启和云端重复收包不能产生重复告警。证据文件用 hash 引用，避免消息和图片不一致。

至少暴露：相机 FPS/丢帧/断流、ISP 错误、预处理/NPU/后处理耗时、端到端延迟、温度/频率/内存/DMA buffer/磁盘、模型版本、事件计数、上传失败、服务重启和最后故障原因。

日志必须结构化、限速、轮转并有磁盘上限；诊断包应能脱离 SSH 汇总这些信息。

### 4.5 安全、隐私和升级

- 禁止默认弱密码，管理接口必须鉴权并区分权限；
- 固件、模型、配置包有版本和完整性校验，最好加入签名验证；
- OTA 失败可回滚，升级中断不能变砖；
- 设备身份、证书、序列号和密钥有安全烧录流程；
- 视频/图片有最小权限、保留期限和删除策略；
- 第三方内核、SDK、模型、数据和调参文件建立许可证清单；
- 工厂测试覆盖相机、存储、网络、NPU、温度、RTC、升级和恢复。

## 5. 最值得研究的“含金量”问题

1. **事件驱动推理**：低成本检测变化，只有疑似事件才触发高质量模型，降低功耗和延迟。
2. **不确定性感知**：将置信度、输入质量、跟踪稳定性和设备健康合成可信度，允许系统明确输出 `unknown`。
3. **持续学习闭环**：误报/漏报自动进入待标注队列，数据、模型、设备和规则版本可追溯。
4. **小模型组合**：检测、分类、跟踪、规则分别承担简单任务，按成本选择性执行。
5. **端侧隐私保护**：只上传事件、匿名化证据或特征，而不是持续上传原始视频。
6. **视觉与控制安全隔离**：用有效期、序列号、权限、限幅和状态机阻止过期视觉结果影响实时控制。
7. **故障感知**：系统知道什么时候“不可信”，并能给出原因和恢复动作。

## 6. 当前最值得先实现的四个基础件

不要先写复杂 UI，先把这四件事做成可复用底座：

1. **相机能力探测与长稳工具**：输出格式、FPS、时间戳、丢帧、错误、温度和内存。
2. **统一视觉消息结构**：版本、序列、时间戳、置信度、有效期、模型版本和健康状态。
3. **板端 AI benchmark**：分别测预处理、NPU、后处理、端到端 P95/P99、内存和温度。
4. **事件状态机和回放测试**：把检测结果变成可去重、可结束、可恢复的业务事件。

完成这四件事后，再针对一个具体现场训练模型和开发接口，项目就不再是一次性 Demo，而是有平台复用价值的产品底座。

## 7. 产品级验收证据

| 方向 | 必须有的证据 |
| --- | --- |
| 相机 | 设备树、格式、FPS、丢帧、断流恢复报告 |
| 图像 | IQ 版本、镜头信息、困难场景样张和输入格式 |
| AI | 数据版本、model card、转换命令、精度和板端性能 |
| 事件 | schema、状态机、幂等性、回放测试、证据图 |
| 可靠性 | 24/72 小时运行、内存/温度/磁盘和重启结果 |
| 故障 | 断相机、断网、模型损坏、写满、杀服务后的行为 |
| 安全 | 鉴权、完整性校验、OTA 回滚、权限和隐私说明 |
| 实时控制 | 视觉域与 1 kHz/200 Hz 域的边界、过期和限幅测试 |
| 量产 | 序列号、版本追踪、工厂测试和诊断包 |

没有命令、日志、报告、回放或测试数据支撑的“应该可以”，不算完成。

## 8. 最终目标

最终交付物应是：一台 RV1126B 设备能够稳定采集真实现场画面，在 NPU 上运行经过量化和回归验证的模型，把瞬时检测转化为带证据、可追溯、可去重、可恢复的时空事件；断网、断流、服务崩溃、存储写满、模型异常和升级失败都有明确行为；视觉结果与实时控制域隔离，并通过时间戳、有效期和安全状态机交互；设备支持远程诊断、签名升级和回滚。
