# 千帆分句流水线与首音频延迟（2026-09-18）

## 改动

千帆 v2 SSE 增量按自然标点组成短句，独立网络生产线程和串行TTS消费线程重叠。
不按字合成；句间共享起播缓冲，只发一次PCM结束标记。短问候不会绕过启动缓冲。
保留原非流式路径，qianfan_streaming=false可回退；默认true仅在local_tts_streaming启用时生效。
有界队列4、回答120字符、整轮PCM45秒、响应262144字节、网络8秒I/O/45秒总限时。
取消关闭实际网络socket，云端文字事件按句合并防止核心事件队列溢出。
UI保留累计完整回复；句子单独用于EchoGuard，保留原疑似回声确认机制。

计时新增cloud_first_token_ms、cloud_first_sentence_ms、tts_first_pcm_ms。
tts_first_audio_ms改显示“起播缓冲就绪”，不再混淆首个PCM与可开始播放。
cloud_ms为完整云端生成，tts_total_ms从首次合成开始到所有分句完成；两者重叠，不可直接相加。

## 板端测试

麦克风关闭，无扬声器播放。固定公开测试问题“请用两句话介绍雨后散步的好处。”，
沿用板端现有密钥/千帆模型，只发固定文字。真实Melo CPU+NPU合成，PCM仅内存计数丢弃。
记录每批到达时刻和时长，以累计已供音频时长估计供应空档；不是实际ALSA或真人听感验收。
旧程序与测试目录分别运行，生产服务仍静音。每组3次，回答内容与网络延迟并不完全相同，
因此不能把组间差值解释为严格的因果加速比。

| 链路 / 缓冲 | 首次PCM交付秒（三次） | 估计供应空档 |
|---|---|---|
| 原串行 / 2.0秒 | 4.800 / 4.278 / 4.158 | 均无 |
| SSE分句 / 2.0秒 | 4.523 / 4.652 / 4.535 | 均无 |
| SSE分句 / 1.2秒 | 3.648 / 3.010 / 3.024 | 第三次470.1ms |
| SSE分句 / 1.5秒 | 3.801 / 4.978 / 4.148 | 均无 |

新增计时表明首PCM约1.41–1.43秒，2秒缓冲交付约2.63–2.75秒。
1.5秒阈值在本样本仍常需等待第二批，因此不是稳定的低延迟方案。
最终保留生产2秒缓冲，未用1.2秒换取明显句间空档。流式已打通，但本批短回答
未证明首音频有稳定下降，当前限制仍是首句生成与Melo启动/供应速度。下一步需在相同文字、
相同分句下测Melo CPU前端/flow与NPU各批成本，不能宣称本轮已解决全部延迟。
