# 从优秀开源实现中学习

以用户问题选择源码，不以 star 数或“大项目都这么做”论证正确性。
好的教学片段应能看清契约、实现、调用者与测试，且其语言版本/运行环境与问题有可比性。
优先使用项目已锁定的依赖及其上游官方文档；缺少合适例子时再联网寻找 1–2 个候选。
用户给出 URL 时实际打开；来源无法访问就说明，不能编造作者意图、行号或实现。

## 导读步骤

1. 明确本轮读什么：例如“初始化失败如何释放 SDK 资源”，限定一个类型、函数或调用链。
2. 记录仓库、版本/tag/commit（可取得时）、文件路径与符号。仅能看到 main 时注明会变化。
3. 读公开契约 → 实现 → 一个调用者 → 相关失败测试；没有测试或没有读到的部分如实说明。
4. 用输入、状态变化、资源归属、输出/错误解释控制流；给出关键片段的位置，不逐行翻译整个文件。
5. 将代码证据与设计解释分开：作者未明确说明的动机标为推断；同时指出局限与另一种合理做法。
6. 映射回 rtctrl：哪些原则能借鉴、哪些依赖和前提不同、哪部分需要重新设计；给用户一个小型迁移练习。

## 可按主题寻找的材料

- SDK 生命周期：本地 RKNN 的 `rknn_api.h` 与对应官方 demo；先确认 SDK/目标 SoC。
- 帧所有权：项目采集端口与 Linux 官方 V4L2 文档/示例；特别追踪借用、归还和设备重用。
- 固定容量并发：项目 SPSC 实现及 README 已列出的 Rigtorp/Boost 上游；对照实际线程模型和内存序。
- 端口与活动模型：项目 ADR 与 README 中 Orocos RTT 上游；分析其运行时依赖是否适合当前问题。
- C++ 资源管理：标准相关材料与 C++ Core Guidelines 原文；区分语言保证和指导性建议。

这些是检索入口，不表示已在本轮读过、评估过，或推荐直接引入依赖。
推荐用户投入大量时间学习某个仓库前，核实其可访问性、相关版本和例子的适用程度。

## 使用源码的边界

给出可定位的本地路径/符号或上游永久链接，摘录仅限讲解所需片段。
学习设计不等于整段搬运；若用户要求引入代码，先确认许可证、归属和依赖要求，再按实现请求处理。
不自动下载整个大仓库、执行外部脚本或安装依赖。用户禁止联网时用本地材料并说明信息边界。
