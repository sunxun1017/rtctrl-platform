# 把理论转化成判断能力

先确定用户要理解的机制与当前约束，避免按术语名单逐个讲解或为展示知识扩大课程。
讲一个概念时，按需要串起：具体问题 → 机制/定义 → 成立前提 → 最小例子 → 失效条件。
类比后回到真实对象和行为，指出类比忽略的细节；公式注明量纲、假设与推导中省略的步骤。

用户问“什么时候用什么”时，先识别真正影响决定的维度，例如：

- 所有权与生命周期：谁创建、借用、转交、释放，失败与退出时由谁清理。
- 并发：生产者/消费者数量、线程归属、共享状态、可见性与同步要求。
- 时间与空间：最坏耗时、是否可阻塞/分配、容量上限、吞吐和端到端时延。
- 平台边界：C/C++ ABI、SDK 版本、SoC/驱动支持与安装依赖。
- 复杂度成本：当前规模下的实现/调试/维护成本，未来变化是否已经有证据。

给出一个有条件的建议和至多几个真正可行的替代方案；必要时用表格比较前提、收益、代价、
不适用条件与验证手段。讲清哪个约束改变会令结论翻转，不笼统宣布某模式“最佳”。
区分项目硬性约束、语言/API 保证、经验判断和待测假设。

## 本项目常见练习切口

这是教学问题索引，不是无需核查即可套用的答案：

| 问题 | 需要理解的理论 | 可让用户验证什么 |
| --- | --- | --- |
| C SDK 句柄怎样封装 | RAII、唯一所有权、移动/复制语义、部分初始化 | 构造中途失败与重复清理时资源归属 |
| 帧交给异步 worker | 借用/拥有、背压、有界队列、停机协议 | release 后消费者是否仍读同一 buffer |
| 队列选锁还是无锁 | happens-before、生产消费拓扑、进展保证 | 改变线程数量后原先不变量是否成立 |
| 用虚接口、函数表还是模板 | 运行时/编译时多态、ABI、注入与测试替身 | 需求变更会改接口、实例还是编译目标 |
| 为什么链接仍报错 | 声明/定义、编译/链接、CMake usage requirements | 哪个 target 编译了定义、谁传播了依赖 |
| 推理快是否代表系统实时 | 吞吐、排队时延、deadline、尾延迟 | 长尾输入或队列积压是否违反完成时限 |

不要把 lock-free 等同于 wait-free 或确定实时；不要把平均速度当最坏时延，或把零拷贝当没有
所有权/同步成本。涉及精确内存序、未定义行为、厂商 API 或不确定细节时查权威资料。

验证可以是手工状态表、最小程序、故障注入或测量；选择能区分竞争假设的最小实验。
教学示例若省略错误处理/线程安全等内容须说明，不能包装成生产可用实现。
